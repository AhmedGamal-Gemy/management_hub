# Tutor Ops Dashboard — Technical Plan

## 1. Product Vision

A single-owner command center for a tutoring business. One person logs in, sees their entire teaching operation — students, sessions, money, curriculum, content, proposals — in one calm, fast interface. No team features, no multi-tenant complexity. Every feature in the 20-day plan is built for exactly this use case.

---

## 2. Architecture Contract

The product runs as the original stack, exactly as Replit ran it. The
UI is fixed: a Vite + React single-page app in `frontend/`. The API is
fixed: the Express server in `backend-express/`. The work ahead is a
feature-by-feature migration of the API to FastAPI in `backend/`
(currently parked, not in the running stack).

**One data path:** The browser talks to exactly one origin. In dev the
Vite server forwards same-origin `/api/*` to Express on internal port
5000 (see `server.proxy` in `frontend/vite.config.ts`, driven by
`API_PROXY_TARGET`).

**`lib/api-spec/openapi.yaml` is the REST contract both sides honor.**
The frontend's hooks (`lib/api-client-react`, generated by Orval) call
`/api/*` paths from that spec. Express implements them today; FastAPI
must implement the same paths and shapes when each domain migrates. If
the spec changes, the client is regenerated — never hand-edited.

**Auth model:** Clerk owns identity. The browser holds the Clerk session
(cookie). Express verifies it via `clerkMiddleware` and takes the user
id as the owner id (`getAuth(req).userId`, demo-user fallback preserved
from the original code). Every data query is scoped by owner id.

**The database schema is the single source of truth for data shape.**
`lib/db/src/schema/management.ts` (Drizzle) defines the tables;
`lib/db/schema.sql` is the hand-ported equivalent applied to Postgres
(drizzle-kit push does not run on this machine). The generated Zod
schemas in `lib/api-zod` define the API shapes.

## 3. Behavioral Contracts

### User lifecycle

A user lands on a public landing page. Sign-in and sign-up are Clerk
pages at `/sign-in` and `/sign-up`. After sign-in the user lands on the
overview dashboard. Protected routes redirect to sign-in when there is no
session. Sign-out is in the sidebar. Every user only ever sees their own
rows — the backend scopes all queries by the verified owner id.

### Navigation contract

The sidebar has five sections — Overview, Teaching, Freelance, Build, and Settings — matching the plan's workspace concept simplified to one user. The sidebar is persistent on desktop and slide-out on mobile. Every sidebar link highlights its active page. Settings allows toggling which sections appear in the sidebar.

### CRUD behavior

All data operations go through the generated React Query client against
`/api/*`. Creating or changing a record invalidates the relevant query
cache so the UI refreshes. Editing opens a modal form pre-filled with
current values. Deleting asks for confirmation first. Every view has a
loading state (skeleton), an empty state (icon, heading, copy, optional
action), and an error state (message, retry button). Search inputs filter
results in real time through the query key.

### AI behavior (planned — not yet built)

Two AI features are planned: session note summarization and a monthly
financial insight. Both will be triggered by an explicit button — AI never
runs automatically. When triggered, the frontend will POST to the FastAPI
backend (same-origin `/api/ai/*`, session cookie attached); the backend
validates the session, calls the model via litellm, and returns the
result for display in a distinctly styled card with an AI badge. If the
AI call fails (rate limit, network error, model unavailable), a clear
error message is shown and the user can retry. Until Days 17–18 land,
these buttons do not exist and no AI calls happen.

### Teaching behaviors (built UI — backend must satisfy it)

- **Students:** searchable list; add/edit modal with full record fields;
  delete with confirmation. Backend: `GET/POST /students`,
  `GET/PATCH/DELETE /students/{id}`, owner-scoped, with per-student
  session counts.
- **Sessions:** planned-session modal (student, class, date, duration,
  rate); mark-as-taught action flips status and payment state; cost is
  computed server-side from duration × rate snapshot. Backend:
  `GET/POST /sessions`, `PATCH/DELETE /sessions/{id}`.
- **Curriculum:** add modal; flag-for-review / mark-current toggle;
  delete with confirmation. Backend: `GET/POST /curricula`,
  `PATCH/DELETE /curricula/{id}`.
- **Income:** read-only rollups (confirmed, estimated, average rate) plus
  the taught-session ledger behind them. Backend: `GET /overview` and
  session listing filtered to taught.

### Freelance behaviors (built UI — backend must satisfy it)

- **Projects:** create modal; advance-status action cycling
  idea → proposal → working → completed; delete with confirmation.
  Backend: `GET/POST /freelancer-projects`,
  `PATCH/DELETE /freelancer-projects/{id}`, plus time-entry
  `GET/POST /freelancer-projects/{id}/time-entries`.
- **Proposals:** log-proposal modal; mark-won action; delete with
  confirmation. Backend: `GET/POST /proposals`,
  `PATCH/DELETE /proposals/{id}`.
- **Money:** expense ledger with add modal and delete; quick log-time
  action against the first active project; net view derived from
  overview minus logged expenses. Backend: `GET/POST/DELETE /expenses`.

### Build behaviors (built UI — backend must satisfy it)

- **Ideas:** capture modal; advance-stage action
  (new → researching → developing); delete with confirmation. Backend:
  `GET/POST /ideas`, `PATCH/DELETE /ideas/{id}`.
- **Ventures:** create modal; advance-stage action
  (idea → research → planning → development); file attachment per
  project. Backend: `GET/POST /venture-projects`,
  `PATCH/DELETE /venture-projects/{id}`.

### File behavior (built UI — backend must satisfy it)

Attaching a file is a three-step flow the UI already implements:
request a signed upload URL (`POST /storage/uploads/request-url`),
PUT the bytes to that URL from the browser, then save the metadata
record (`POST /files`). Listing filters by entity (`GET /files`).
The backend must implement the signing endpoint against its object
store and persist the record owner-scoped. Maximum file size is 10MB.

## 4. Deployment Strategy

**Current phase: local development only.** No production hosting is set up. Everything runs through Docker Compose on the developer's machine.

**Local environment:** One command — `docker compose up --build` — starts the frontend (Vite dev on 5173, forwarding `/api` to Express), the Express API (port 5000, internal), and Postgres. Fill in `.env` from `.env.example` first (Clerk keys and Postgres password at minimum).

**Environment variables (see `.env.example` for the full list):**
- `PORT`, `BASE_PATH` — required by `vite.config.ts` (5173 and `/` locally)
- `API_PROXY_TARGET` — where Vite dev forwards `/api` (`http://express:5000` in compose)
- `VITE_CLERK_PUBLISHABLE_KEY` — Clerk key for the UI (refuses to boot without it)
- `CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY` — Clerk keys for the Express API
- `POSTGRES_USER/PASSWORD/DB`, `DATABASE_URL` — Postgres (container host is `db`)
- `GROQ_API_KEY`, `LITELLM_MODEL`, `CLERK_JWKS_URL`, `FRONTEND_DIST` — parked FastAPI settings, unused until migration

**Deployment is dual-config (see TECHNICAL_PLAN.md section 6).**
Local dev runs `docker compose up` (frontend:5173, express:5000, db:postgres). Replit reads `.replit` + `replit.nix` instead and exposes a single external port, with the built SPA served on the same port as the API.

**Future production deployment beyond Replit (not now, but the architecture supports it without changes):**
- Frontend static files served by the backend container (single deployable)
- Backend + db deploy to any container host (Render, Fly, Railway)
- No code changes required — the same Compose file shapes production services

## 5. Tools

| Tool | Purpose | Why this one |
|---|---|---|
| **Vite + React 19** | Product UI (already built) | The existing SPA is the product; Wouter routing, Tailwind v4, vendored shadcn/ui |
| **Clerk** | Authentication | Already wired end-to-end (sign-in/up pages, session cookie, backend verification) |
| **Orval** | API client codegen | Regenerates `lib/api-client-react` hooks and `lib/api-zod` schemas from `openapi.yaml` — never hand-edit generated files |
| **FastAPI** | Backend framework (parked) | Async-native, Pydantic validation; migration target for `/api/*`, plus `/ai/*` later |
| **Postgres** | Database | Local `db` service in compose; Drizzle schema in `lib/db` (+ `schema.sql` port) is the source |
| **litellm (Python package)** | AI model access from the backend | One package, 100+ providers, model chosen by env value — zero code changes when switching models |
| **Groq** | AI inference provider | Free tier, very fast inference, good quality for structured tasks like summarization and insight generation |
| **Docker Compose** | Local orchestration | One command starts frontend, backend, and Postgres; no local Node.js or Python installation needed |
| **TanStack React Query** | Frontend data fetching and caching | Generated hooks built on it; handles loading, error, and cache states declaratively |
| **pnpm workspaces** | JS package management | Required — the frontend consumes `workspace:*` libs that npm cannot resolve |
| **lucide-react** | Icon set | Already in the UI; tree-shakeable |
| **date-fns** | Date formatting and manipulation | Lightweight, modular, already in the UI |
| **Pydantic** | Request/response validation on FastAPI | Enforces the contract between frontend and backend at the API boundary |
| **PyJWT + cryptography** | Clerk JWT verification on backend | Validates the session token against the Clerk JWKS (RS256) |
| **httpx** | JWKS fetching (and future backend HTTP calls) | Async-native, works cleanly inside FastAPI |

## 6. Execution Rhythm

The whole product runs as the original stack. The remaining work is the
feature-by-feature migration of the API from Express to FastAPI, one
domain at a time, each verified by driving the real UI against it: every
button the frontend already renders must keep working after its domain
migrates.

**Phase 1 — Running original (done):** workspace boots
(`docker compose up`), Postgres schema applied, Express serving `/api/*`
exactly as on Replit.

**Phase 2 — Migration domains:** students + sessions, curricula,
freelance (projects, proposals, time entries, expenses), build (ideas,
ventures, files), overview + activity aggregates, storage uploads — each
implemented in FastAPI per `openapi.yaml` and verified through the
existing pages before Express stops serving that domain.

**Phase 3 — AI:** session summarizer and financial insight via litellm,
wired to UI buttons with error states.

**Phase 4 — Polish + launch:** full walkthrough of every page, edge
cases, mobile check, Replit deploy verification.

Each phase has concrete deliverables that can be verified independently
by clicking through the built UI.

## 7. What Is Explicitly Out of Scope

- Multi-user / multi-tenant support (one owner id per login; every query scoped)
- Team invitations, roles, or permissions beyond a single login
- Payment processing with real payment providers (Stripe, PayPal)
- Mobile native apps (responsive web only)
- Email notifications
- Data export / import
- Third-party integrations beyond Groq via litellm
- Production hosting (local dev only until final verification is complete)
